## Project Template-Dotnet: Communication Design Document

**Date:** May 23, 2025

**Version:** 1.0

### Introduction

This document summarizes the comprehensive communication design architectural decisions for "Project Template-Dotnet." It covers project context, frontend URL structure, backend API design, security measures, error handling, performance and caching strategies, and finally, monitoring and scalability considerations. The aim is to provide a clear blueprint for a robust, modular, secure, and optimized system.

---

### 1. Project Context & Objectives

* **Primary System Configurations**:
    * **Configuration 1**: Standalone In-App (MAUI) with no backend authentication, data is local.
    * **Configuration 2**: MAUI app interacting with a multi-user API backend with authentication.
* **Main Route Categories**:
    * **Public Routes**: Accessible to all (e.g., Home, Product Listings, Login/Registration for Config 2).
    * **Authenticated/Private Routes (Config 2) or Local/Session-based Routes (Config 1)**: For user-specific content and actions.
    * **Admin Routes & General Informational Pages**: Explicitly deferred for future versions, but the architecture should accommodate them.
* **Key Defined Pages/Views**:
    * **Public**: Home, Product List, Product Detail, Login (Config 2), Registration (Config 2), Registration Success (Config 2).
    * **Authenticated/Private (Config 2) or Local/Session (Config 1)**: Current Order/Cart, Checkout (single page for shipping/payment), Order Confirmation, Order History, Order Detail, User Profile (Config 2).
* **New Feature - Product Search**: A product search capability has been identified as a requirement, impacting product listing URLs and API endpoints.

---

### 2. Frontend URL Structure

* **General Conventions**:
    * **Naming**: Kebab Case (e.g., `/product-detail`).
    * **Root Path**: `/` for the Home Page.
* **Parameter Usage**:
    * **Path Parameters**: For specific resource identification (e.g., `{uuid}`, `{product-name-slug}`). Uses UUIDs for resource identifiers.
    * **Query Parameters**: For sorting, filtering, pagination, and search (e.g., `?search={searchTerm}&sort_by=price`).
* **Defined Frontend URL Structures**:
    * `/products`: Product list with query parameters for search, sort, filter.
    * `/products/{uuid}/{product-name-slug}`: Product detail.
    * `/cart`, `/checkout`, `/orders`, `/orders/{uuid}`, `/order-confirmation/{uuid}` for order-related flows.
    * `/login`, `/register`, `/registration-success`, `/profile` for user authentication and management (Config 2).
* **SEO Considerations**:
    * Descriptive URLs using Kebab Case and slugs (e.g., `/products/{uuid}/{product-name-slug}`).
    * Importance of implementing `rel="canonical"` link elements to avoid duplicate content.
* **Sensitive Data**: No PII or unnecessary tokens in URLs. UUIDs are used for exposed resource IDs.

---

### 3. Backend API Design

* **API Style**: RESTful.
* **Base Path & Versioning**: `/api/v1/`. URL-based versioning.
* **Resource Naming**: Plural nouns for collections (e.g., `/api/v1/products`), Kebab Case for multi-word segments. UUIDs for resource identifiers.
* **Key API Endpoints (`/api/v1/...`)**:
    * **Products**:
        * `GET /products`: List products (supports pagination, filtering, sorting, `search={searchTerm}`).
        * `GET /products/{uuid}`: Get a single product.
    * **Cart Management (Dedicated Resource)**:
        * `GET /cart`, `POST /cart/items`, `PUT /cart/items/{itemId}`, `DELETE /cart/items/{itemId}`, `POST /cart/validate`.
        * Client-side (MAUI) to use optimistic updates and debouncing for responsive UX.
    * **Orders (Authenticated)**:
        * `POST /orders`, `GET /orders` (with pagination, filter, sort), `GET /orders/{uuid}`, `PUT /orders/{uuid}` (for actions like cancellation).
    * **User Profile (Authenticated)**: `GET /profile`, `PUT /profile`.
    * **Authentication**: Endpoints like `/auth/login`, `/auth/register`, etc., will be defined.
* **Query Parameter Standards**:
    * Pagination: `page={pageNumber}`, `limit={numberOfItems}`.
    * Sorting: `sortBy={attributeName}`, `sortOrder={asc|desc}`.
    * Filtering/Search: Resource-specific (e.g., `status={value}`, `category={value}`, `search={searchTerm}`).
* **Nested Resources**: Primarily for cart items (`/cart/items/{itemId}`). Extensive nesting avoided for V1 simplicity.
* **Batch Processing**: Deferred for V1.

### 4. Security & Access Management

* **Authentication Modes**: Configuration 1 (no backend auth), Configuration 2 (backend auth).
* **User Roles (Config 2)**: `User` (standard authenticated actions) and `Admin` (defined for future use). Unauthenticated access for public resources.
* **Authentication Methods (Config 2)**:
    * Local: Email & securely hashed password (credentials in a separate DB).
    * Google: OAuth 2.0 / OpenID Connect.
    * Account Linking for same-email identities.
* **API Authentication (Config 2)**:
    * **JSON Web Tokens (JWTs)**: Issued on login (access & refresh tokens).
    * Client must store tokens securely (e.g., platform-specific secure storage).
* **API Endpoint Protection (Config 2)**:
    * Private endpoints require a valid JWT. Middleware validates JWT and checks roles.
* **Rate Limiting & Abuse Protection (Config 2 API)**:
    * Dual approach: Infrastructure-level and application-level (on sensitive endpoints like login, registration).
* **CORS Policy (Config 2 API)**: Will be configured for flexibility with future web clients.
* **Temporary Secure URLs (Password Reset, Email Verification)**: Important features for local accounts, but implementation is **deferred post-MVP (V1)**. Architecture should accommodate them.
* **API Keys**: Deferred for V1 (no specific use case identified).

### 5. Error Handling & HTTP Status Codes

* **Standard HTTP Status Codes**: Consistent use of codes like `200 OK`, `201 Created`, `204 No Content`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `429 Too Many Requests`, `500 Internal Server Error`.
* **Standardized JSON Error Responses**:
    * All API error responses (4xx, 5xx) will use the **`ProblemDetails`** (RFC 7807) format.
    * Includes core fields: `type`, `title`, `status`, `detail`, `instance`.
    * For validation errors (`400 Bad Request`), `ProblemDetails` will be extended with an `errors` property detailing field-specific issues.
* **Domain Error Mapping**: Internal domain errors will be translated into appropriate `ProblemDetails` objects and HTTP status codes at the API/Application layer boundary.

### 6. Performance & Caching Strategy

* **General**: Strategies address both configurations and the Product Search feature's impact.
* **Configuration 1 Caching (Standalone MAUI)**: Application-level in-memory caching for local data to improve UI responsiveness.
* **Frontend Caching (MAUI Client - Config 2)**:
    * Targets: Paged product lists (including search/filter/sort results), individual product details.
    * Duration: Configurable, short-to-medium term (e.g., 5-15 mins).
    * Modularity: Abstracted caching logic.
* **Backend Caching (API - Config 2)**:
    * Targets: `GET /api/v1/products` results (common queries, searches).
    * Initial Mechanism: `IMemoryCache` (in-process).
    * Modularity: Abstracted via an interface (e.g., `IServerCacheService`) to allow future use of distributed cache (e.g., Redis) with minimal changes.
* **HTTP Caching Headers (API - Config 2)**: Emission of `Cache-Control` and `ETag` headers for cacheable resources.
* **Cache Invalidation (Backend `IMemoryCache` - Config 2)**:
    * **Primary Strategy (Most Important)**: **Event-driven invalidation** using domain events for proactive cache updates within the same process.
    * **Secondary Strategy**: Time-based expiration as a fallback.
    * **Note**: Event-driven invalidation for `IMemoryCache` is in-process specific; a distributed cache would require a different invalidation mechanism.

### 7. Monitoring & Scalability

* **API Request Logging (Config 2)**:
    * Comprehensive logging (path, method, status, time, user, IP, etc.) using **Serilog**. Sensitive data masked.
    * Storage: Rotating files. Guidance for sinking to a self-hosted database, with users responsible for DB log retention/cleanup.
* **Device Logging (MAUI App - Config 1 & 2)**: Local file-based logging with rotation and max 1-week retention.
* **API Monitoring (Config 2)**:
    * Metrics: Request rate, error rate, latency, host resource utilization.
    * Guidance: Documentation will suggest open-source tools (e.g., Prometheus, Grafana).
* **Usage Analytics (FSD CC-AN-001 - Config 2)**: Separate, toggleable module.
* **Audit Logging**: Out of scope for V1.
* **API Scaling Strategies (Config 2)**:
    * Application: Stateless services, horizontally scaled with a load balancer.
    * Database (PostgreSQL): Documentation will note PostgreSQL's scalability options for user implementation.
    * CDNs: Primarily for a future website.
* **Error Tracking & Alerting (Config 2)**:
    * Tracking via Serilog.
    * Alerting: No built-in engine. Documentation will guide users on leveraging open-source tools (e.g., ELK, Prometheus/Alertmanager) with self-hosted log/metric stores.

### Conclusion

This document outlines the core architectural decisions made for the "Project Template-Dotnet." By adhering to these guidelines, the project aims to establish a well-structured, secure, maintainable, and performant foundation suitable for its intended use as a boilerplate and for future expansion.
