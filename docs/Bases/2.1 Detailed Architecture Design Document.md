# Project Template-Dotnet: Detailed Architecture Design Document

**Version:** 1.0
**Date:** May 23, 2025

## Introduction

This document provides a comprehensive summary of the architectural decisions, strategies, and organizational structure for "Project Template-Dotnet." It is the culmination of a structured decision-making process, building upon the initial "Functional Specification Document" and "Final Architecture Document" provided, and refined through detailed discussions. The goal of this project is to create a robust, modular .NET 9 boilerplate demonstrating best practices in Clean Architecture, Domain-Driven Design (DDD), and Command Query Responsibility Segregation (CQRS) without relying on the MediatR NuGet package.

This summary is organized into the key architectural areas discussed:

1.  Needs & Constraints Verification
2.  Hosting & Deployment
3.  Back-End Design
4.  Front-End Design
5.  Data & Database Management
6.  Event & Asynchronous Flow Management
7.  Security & Performance
8.  Observability & Maintenance
9.  Folder Structure & Project Organization

## Section 1: Needs & Constraints Verification

**1. Project Goal:**
    * **Primary Objective:** To develop "Project Template-Dotnet," a .NET 9 boilerplate project.
    * **Architectural Focus:** Demonstrate best practices in Clean Architecture, Domain-Driven Design (DDD), and Command Query Responsibility Segregation (CQRS).
    * **Key Constraint:** CQRS implementation will be custom, explicitly avoiding the MediatR library.
    * **Initial Implementation:** A simple product purchasing application to showcase the template's capabilities.
    * **Purpose:** Serve as a robust and modular foundation for future .NET projects.

**2. Application Type:**
    * The project delivers a **reusable template** rather than a single, fixed application.
    * The template is designed to generate applications with two primary configurations:
        * **Configuration 1 (Standalone):** A .NET MAUI mobile application where all logic (including business and data access) runs in-process. It features no backend authentication, with data typically local to the device or session.
        * **Configuration 2 (Client-Server):** A .NET MAUI mobile application acting as a client to an ASP.NET Core API backend. This configuration supports multiple authenticated users.

**3. Main Features and Functionalities:**
    * **Product Catalog Module:**
        * View a list of available products (name, description, price, image).
        * Product Search capability.
        * Data sourced from fake data generators for demonstration.
    * **Order Management Module:**
        * Add products to an order, specifying quantity.
        * View current order details (products, quantities, prices, total).
        * Modify order item quantity (removal if quantity is zero).
        * Remove products from an order.
        * Add/select shipping address.
        * Add/select payment details (simulated).
        * Validate order (triggers `OrderValidatedEvent`).
        * View current and past order status.
        * Order lifecycle management (`Draft`, `Pending_Payment`, `Payment_Failed`, `In_Progress`, `Shipped`, `Delivered`, `Cancelled`) driven by domain events.
    * **Finance Service Module (Simulated):**
        * Handles `OrderValidatedEvent` (or `PaymentProcessingRequestedEvent`).
        * Simulates payment processing (configurable success/failure) and invoice generation.
        * Raises `OrderPaymentConfirmedEvent` or `OrderPaymentFailedEvent`.
    * **Shipping Service Module (Simulated):**
        * Handles `OrderPaymentConfirmedEvent`.
        * Simulates shipment processing with configurable delays.
        * Raises `OrderShippedEvent` and `OrderDeliveredEvent`.
    * **Realtime Notification Module (Modular):**
        * Notifies users of order status changes (subscribes to relevant domain events).
        * Designed to be easily enabled/disabled.
    * **Cross-Cutting Concerns:**
        * **Authentication (Configurable):**
            * Mode 1: No authentication (for Config 1).
            * Mode 2 (for Config 2): Google OAuth 2.0/OpenID Connect, Local username/password (securely stored in a separate DB), Account linking. Modularity for provider selection.
        * **Localization & Internationalization:** UI text and data formatting for at least two languages (e.g., English, French).
        * **Automated Testing:** Unit tests for core logic, integration tests for component interactions. High test coverage is a goal.
        * **Data Persistence (Modular & Configurable):**
            * Database Agnostic Design (core application/domain).
            * Support for SQLite (typically for Config 1).
            * Support for PostgreSQL (typically for Config 2).
            * Support for Entity Framework Core (ORM option).
            * Support for Dapper (ORM option).
        * **API Layer (Modular & Configurable for Config 2):**
            * Controller-Based API support.
            * Minimal API support.
            * Request validation, API versioning.
        * **Frontend:** .NET MAUI mobile client (iOS, Android).
        * **Performance:** Optimized design, asynchronous operations, responsive UI.
        * **Analytics (Modular for Config 2):** Basic usage analytics, toggleable, platform TBD.

**4. Target Users:**
    * **For the Template:** Developers using it as a starting point for new applications.
    * **For the Sample Product Purchasing Application:**
        * Configuration 1: A single, anonymous user interacting with the app locally.
        * Configuration 2: Multiple authenticated users.
    * No more specific user personas are defined at this stage.

**5. External Integrations:**
    * **Authentication (Config 2):** Integration with Google for OAuth 2.0 / OpenID Connect.
    * **Payment Gateways:** None; payment processing is explicitly simulated within the Finance Service Module.
    * **Analytics (Config 2):** No specific external platform defined yet; the module will provide hooks for future integration.
    * No other external services or third-party APIs are required for the initial version.

## Section 2: Hosting & Deployment

**1. Hosting Environment (Configuration 2 API Backend):**
    * **Strategy:** Cloud-agnostic.
    * **Rationale:** To provide maximum flexibility for developers, allowing deployment on any preferred cloud provider (AWS, Azure, GCP, etc.) or on-premise infrastructure. The template will focus on delivering an application that adheres to principles compatible with diverse hosting environments rather than targeting a specific one.

**2. Orchestration & Containerization (Configuration 2 API Backend):**
    * **Primary Tooling:** Docker.
        * The template will include `Dockerfiles` for containerizing the ASP.NET Core application components.
        * Example `docker-compose.yml` files will be provided to facilitate local development setups and demonstrate how to run the application with its dependencies (e.g., a PostgreSQL database container, a Traefik container for reverse proxy/load balancing).
    * **Kubernetes:**
        * The application architecture will be designed to be Kubernetes-friendly (e.g., stateless services, configurable ports, health checks).
        * While full Helm charts or operator implementations are out of scope for the template, documentation may include guidance or considerations for deploying to a Kubernetes environment.
    * **Relevance:** These considerations apply primarily to **Configuration 2**. Configuration 1 runs locally on the MAUI device.

**3. Continuous Integration/Continuous Delivery (CI/CD):**
    * **Platform:** **GitHub Actions**.
    * **Scope of CI Pipeline:**
        * **Linting:** Ensure code quality and consistency.
        * **Unit Tests:** Automated execution of unit tests (NUnit will be the framework for .NET).
        * **Integration Tests:** Automated execution of integration tests.
        * **Build:** Compiling the application and building necessary artifacts (e.g., Docker images for the backend services).
    * **Deployment (CD):** Deployment steps will **not** be included in the sample CI/CD pipeline.
        * **Rationale:** Deployment is highly specific to the chosen hosting environment and organizational practices. The template will provide build artifacts, and the implementer will be responsible for deploying them.
    * **Deliverable:** A sample GitHub Actions workflow file (`.yml`) will be included in the template to demonstrate the defined CI stages.

**4. Infrastructure as Code (IaC):**
    * **Strategy:** **No IaC scripts** will be provided as part of the template.
    * **Rationale:** Given the cloud-agnostic approach and the desire to keep the template focused on application architecture, IaC is considered an implementation detail best left to the end-user, who can choose their preferred tools (Terraform, Pulumi, Bicep, CloudFormation, etc.) based on their target environment.

**5. Scale and Traffic Volume (Configuration 2):**
    * **Focus:** The template will emphasize **scalable architectural patterns** (e.g., stateless services suitable for horizontal scaling, efficient data access).
    * **Guidance:** Documentation will highlight these patterns and how they contribute to scalability.
    * **Sizing:** No specific target scale (e.g., requests per second, number of users) or traffic volume will be used for pre-defined resource sizing in examples. The template is intended to be a generic foundation adaptable to various load requirements.

## Section 3: Back-End Design

**1. Core Framework & API Style (Primarily for Configuration 2):**
    * **Framework:** The backend will be developed using **.NET 9** and **ASP.NET Core**.
        * **Rationale:** Leverages the latest features, performance improvements, and long-term support from the .NET ecosystem, aligning with the project's goal of being a modern boilerplate.
    * **API Layer Modularity:** The template will provide configurable options for exposing functionalities:
        * **ASP.NET Core MVC Controllers:** For a traditional, feature-rich approach to API development.
        * **Minimal APIs:** For a lightweight, concise syntax for creating HTTP APIs, suitable for simpler endpoints or specific performance needs.
        * **Rationale:** Offers developers flexibility to choose the API style that best fits their project requirements or team preferences, enhancing the template's adaptability.

**2. Domain-Driven Design (DDD):**
    * **Adoption:** DDD is a foundational architectural principle for this project.
    * **Key Concepts to Implement:**
        * **Entities:** Objects with a distinct identity that persists over time.
        * **Aggregates:** Clusters of associated objects (entities and value objects) treated as a single unit for data changes, with an aggregate root.
        * **Value Objects:** Immutable objects defined by their attributes rather than a unique identity.
        * **Repositories:** Abstractions for data access, mediating between the domain and data mapping layers.
        * **Domain Services:** Operations that don't naturally fit within an entity or value object.
        * **Domain Events:** To capture significant occurrences within the domain, crucial for decoupling modules and implementing CQRS. **The handling and dispatch of these domain events will also be custom-implemented, avoiding reliance on the MediatR package.**
    * **Rationale:** DDD helps in tackling complex business logic by aligning the software model with the business domain, leading to more maintainable, understandable, and scalable applications.

**3. Database Access Strategy:**
    * **Architectural Principle:** Adherence to **Clean Architecture**. The domain and application layers will be designed to be persistence ignorant.
        * **Rationale:** Promotes separation of concerns, testability, and flexibility in choosing or changing data persistence technologies.
    * **Pattern:** The **Repository Pattern** will be used to abstract data persistence logic.
    * **ORM/Data Access Modularity:** The template will provide interchangeable data access implementations:
        * **Entity Framework Core (EF Core):** A feature-rich Object-Relational Mapper (ORM).
        * **Dapper:** A lightweight micro-ORM focusing on performance with raw SQL capabilities.
    * **Rationale:** Allows developers to select the data access technology that best suits their performance needs, existing expertise, or database features, making the template more versatile.

**4. Scalability & CQRS Strategy:**
    * **Core Concern:** High scalability is a non-functional requirement for Configuration 2.
    * **Architectural Patterns for Scalability:**
        * **Command Query Responsibility Segregation (CQRS):** Read and write operations will be segregated. This allows for independent scaling and optimization of read and write paths.
            * **Rationale:** Improves performance by allowing tailored data models and access strategies for queries versus commands; enhances scalability by distributing load.
        * **Stateless Services:** Application services exposed via the API will be designed to be stateless.
            * **Rationale:** Simplifies horizontal scaling, as any instance of a service can handle any request without relying on session affinity.
        * **Asynchronous Operations:** Leveraging `async/await` throughout the backend for I/O-bound operations.
            * **Rationale:** Improves responsiveness and throughput by efficiently using server resources.
    * **CQRS and Eventing Implementation Detail (Key Constraint):**
        * **No MediatR:** The project will **explicitly avoid** the MediatR library for all its internal messaging patterns, including the dispatch and handling of commands, queries, notifications, and **domain events**.
        * **Custom Implementation:** The template will feature its own, self-contained mechanisms (e.g., custom dispatchers, specific interfaces) for these purposes.
        * **Rationale (Implied by constraint):** To provide a boilerplate that is not dependent on this specific third-party library, offering developers a clearer understanding of the underlying patterns or allowing for a more tailored, lightweight implementation.

## Section 4: Front-End Design

**1. Front-End Framework & Application Type:**
    * **Framework:** **.NET MAUI (Multi-platform App UI)**, integrated within the .NET 9 ecosystem.
        * **Rationale:** Enables cross-platform development for mobile (iOS, Android) from a single C# codebase, aligning with the project's .NET focus.
    * **Application Type:** Client-side application.
        * **Rationale:** .NET MAUI applications are compiled and run natively on the target device, managing their own UI and state. This is distinct from server-side rendering.

**2. Styling Approach:**
    * **Primary Method:** **XAML Styling**. This includes the use of:
        * `Style` resources
        * `ResourceDictionary` for theme and style organization
        * `ControlTemplates` for customizing control appearance
        * **Rationale:** XAML styling is the native, most comprehensive, and recommended approach for UI customization in .NET MAUI, offering fine-grained control and a declarative syntax.
    * **Supplementary Method:** **CSS (Cascading Style Sheets)**.
        * Can be used where .NET MAUI directly supports it for styling visual elements.
        * **Rationale:** Offers an alternative styling paradigm that might be familiar to developers with a web background and can be convenient for certain styling tasks. The use is conditional on MAUI's built-in support, adhering to the principle of avoiding third-party styling libraries.
    * **Guiding Principle:** Adherence to .NET MAUI best practices and leveraging built-in styling capabilities.

**3. State Management & MVVM (Model-View-ViewModel):**
    * **Core Pattern:** **MVVM**.
        * **Rationale:** MVVM is the standard architectural pattern for XAML-based applications (including MAUI), promoting separation of concerns between the UI (View), UI logic (ViewModel), and data/business logic (Model), which enhances testability and maintainability.
    * **Implementation Details:**
        * Standard .NET features: `INotifyPropertyChanged` interface for property change notifications from ViewModels to Views, and `ObservableCollection<T>` for collections that automatically update the UI upon changes.
        * **`CommunityToolkit.Mvvm` NuGet Package:** This Microsoft-owned and supported library will be used, specifically for its **source generators**.
            * `[ObservableProperty]` attribute to generate `INotifyPropertyChanged` implementations.
            * `[RelayCommand]` attribute to generate `ICommand` implementations.
            * **Rationale:** Significantly reduces boilerplate code associated with MVVM, improves developer productivity, and is considered a best practice in modern .NET and MAUI development. Its use is justified as it enhances built-in patterns rather than introducing a heavy, opinionated third-party framework.

**4. Navigation:**
    * **Approach:** **.NET MAUI Shell**.
    * **Features Leveraged:**
        * URI-based navigation (e.g., `GoToAsync("//route")`).
        * Flyout menus.
        * Tabbed navigation.
        * Hierarchical navigation within Shell sections.
    * **Rationale:** .NET MAUI Shell is the recommended, built-in solution for most MAUI applications, providing a robust and standardized structure for application navigation. It simplifies complex navigation scenarios and aligns with the "URL-like paths" for views identified in the project documentation.

## Section 5: Data & Database Management

**1. Database Type & Engines:**
    * **Type:** **SQL** relational databases.
        * **Rationale:** Aligns with the structured nature of data in a product purchasing application and the mature tooling available for relational databases.
    * **Engines (Modular):**
        * **SQLite:** Primarily for **Configuration 1** (standalone MAUI app).
            * **Rationale:** Lightweight, serverless, self-contained, suitable for local in-app storage.
        * **PostgreSQL:** Primarily for **Configuration 2** (multi-user API backend). This includes a separate PostgreSQL database or schema for storing local authentication credentials securely.
            * **Rationale:** Robust, open-source, feature-rich RDBMS suitable for scalable, multi-user applications.

**2. Schema Versioning & Migrations:**
    * **SQLite (Config 1 with EF Core):** **EF Core Migrations** will be used.
        * **Rationale:** Integrated tooling within the EF Core ecosystem, suitable for managing schema changes directly by the application for local databases.
    * **PostgreSQL (Config 2):** Migrations will be **DBA-led or managed by external, script-based processes.**
        * **Rationale:** Provides greater control and separation of concerns for production database environments. The application (using EF Core) will define its model to be compatible with this externally managed schema. The template may offer guidance on using EF Core to generate initial SQL scripts that DBAs can then adapt and manage. This ensures the application is modular and can adapt to different database management workflows.

**3. Multi-Tenancy:**
    * **Strategy:** **Not supported** and not a requirement for the template.
        * **Rationale:** Keeps the initial template simpler and focused on core application features. Multi-tenancy adds significant complexity.

**4. Performance Optimization (Database Level):**
    * **Indexing Strategy:**
        * **Clustering Keys:** For tables with GUID/UUID primary keys (used for external identification/API exposure), these will **not** be the clustered index. A separate `INT` or `BIGINT` auto-incrementing column will serve as the **clustered key**.
            * **Rationale:** Improves performance of range scans and reduces index fragmentation compared to using GUIDs as clustered keys.
        * **Other Indexes:** Appropriate non-clustered indexes will be defined as needed to optimize query performance.
    * **Query/Command Optimization:** Emphasis on writing efficient SQL queries and commands, whether through EF Core or Dapper.
    * **Partitioning:** Not a primary focus for the template.
        * **Rationale:** Advanced feature, implementation is highly specific to data volume and usage patterns, making it less suitable for a generic template.

**5. Consistency Requirements:**
    * **Commands (Writes - for Config 2):** Must achieve **strong consistency** and be **transactional** (ensuring atomicity and providing rollback capabilities on failure).
        * **Rationale:** Critical for maintaining data integrity in operations like order creation or inventory updates.
    * **Queries (Reads - for Config 2, especially via CQRS):** The goal is to display updated data with the **lowest possible latency**. This means striving for near real-time data or very fast eventual consistency for read models.
        * **Rationale:** Provides a good user experience by showing fresh data, while acknowledging that CQRS read models might have a slight delay in reflecting writes.
    * **User Experience (Client-Side):** All client-initiated operations (especially commands) must be **asynchronous**. The UI should remain responsive and non-blocking during backend processing.
        * **Rationale:** Essential for modern application usability.

**6. Search Engine (for Product Search):**
    * **Strategy:** **No third-party search engine** (e.g., Elasticsearch, Meilisearch).
    * **Implementation:** Product search functionality will rely on **database-intrinsic capabilities** (e.g., SQL `LIKE` queries, PostgreSQL Full-Text Search if applicable) or custom application-level logic.
        * **Rationale:** Aligns with the principle of minimizing external dependencies and avoiding IaC for the base template.

**7. Concurrency Control:**
    * **Strategy:** The template will aim to demonstrate **Optimistic Concurrency Control**.
    * **Implementation Example:** Using a version property (e.g., `rowversion`/`timestamp` or a dedicated version number column) in relevant entities (like `Product`). When an update is attempted, the system will check this version to ensure the data hasn't changed since it was last read.
        * **Rationale:** A common and effective best practice for handling concurrent data modifications in web/API applications without resorting to pessimistic locking, thus improving scalability and user experience by gracefully handling conflicts.

## Section 6: Event & Asynchronous Flow Management

**1. Asynchronous Processing Requirement:**
    * **Necessity:** Asynchronous processing is fundamental to the architecture.
    * **Use Cases:**
        * Decoupled inter-module communication via domain events (e.g., Order module events triggering actions in Finance or Shipping modules).
        * Offloading tasks such as simulated payment and shipping processes.
        * Driving real-time notifications to users based on backend events.
        * Enhancing overall application responsiveness and scalability by preventing blocking operations, particularly for client-initiated commands.
    * **Rationale:** Ensures a non-blocking user experience, improves system resilience, and allows for better resource utilization.

**2. CQRS and Event Sourcing:**
    * **CQRS (Command Query Responsibility Segregation):** A core architectural principle to be implemented. Read and write stacks will be separated.
        * **Rationale:** Optimizes data access for reads and writes independently, improves scalability, and enhances separation of concerns.
    * **Event Sourcing:** **Explicitly out of scope** for this template. Entities will store their current state.
        * **Rationale:** While powerful, Event Sourcing adds significant complexity. The template will focus on demonstrating DDD with current state persistence and domain events. The distinction between domain events (notifications of things that happened) and event sourcing (using events as the primary source of truth for state) will be clearly maintained.

**3. Event Mechanisms (Backend - Modular Monolith):**
    * **Custom, MediatR-Free Implementation:** The project will implement its own mechanisms for handling commands, queries, and domain events, adhering to best practices without using the MediatR library.
        * **Core Components:**
            * **Interfaces:** `ICommand`, `ICommandHandler<TCommand>`, `IQuery<TResult>`, `IQueryHandler<TQuery, TResult>`, `IDomainEvent`, `IDomainEventHandler<TEvent>`.
            * **DI-Based Dispatcher:** A central dispatcher service (or separate dispatchers for commands, queries, events) will be implemented. This service will use Dependency Injection (e.g., `IServiceProvider`) to resolve and invoke the appropriate registered handlers.
        * **Rationale:** Provides a lightweight, transparent, and educational approach to CQRS/eventing patterns, avoiding third-party library dependencies for this core mechanism and aligning with industry best practices for custom implementations.
    * **Transactional Outbox Pattern for Critical Domain Events:**
        * **Mechanism:** Domain events raised during a business transaction (e.g., `OrderPaymentConfirmedEvent`) will be saved to a dedicated "Outbox" table within the same database transaction as the business entity changes. A separate background process will then reliably read from this outbox and dispatch the events to their respective `IDomainEventHandler`s (via the DI-based dispatcher).
        * **Rationale:** Guarantees that critical domain events are not lost if the application crashes after the main transaction commits but before events are dispatched. Ensures atomicity for state changes and their corresponding event publications. This is a key best practice for reliable event-driven architectures within a monolith or microservices.
    * **Initial Scope:** Event handling will occur in-process within the modular monolith. The design should allow for future extension to distributed messaging if needed, but this is not part of the initial template implementation.

**4. Event Handler Idempotency:**
    * **Requirement:** Due to the at-least-once delivery guarantee provided by the Transactional Outbox pattern, all `IDomainEventHandler` implementations must be designed to be **idempotent**.
        * **Rationale:** Ensures that if an event is processed multiple times (e.g., due to retries after a transient failure), it does not result in incorrect data or duplicated side effects.

**5. Real-time Client Updates:**
    * **Technology Choice:** **SignalR** will be used for real-time communication between the backend (Configuration 2) and the MAUI client.
    * **Modularity:** The real-time notification module will be designed with abstractions (e.g., an `IRealtimeNotificationService` interface) so that SignalR is an implementation detail. This maintains flexibility and testability.
        * **Rationale:** Adheres to the project's principles of modularity and genericity, even when a specific technology like SignalR is chosen for the primary implementation.

**6. Message Delivery Guarantees (for Critical Domain Events via Outbox):**
    * **Delivery:** **At-least-once delivery** is ensured by the outbox pattern.
    * **Retries:** The outbox poller mechanism inherently supports retries (if an event fails to process and isn't marked as complete, it will be picked up again). More sophisticated retry policies can be built into handlers or the dispatcher if needed.
    * **Dead-Letter Queue (DLQ) Concept:** While the template won't implement a full automated DLQ system, the outbox pattern facilitates identifying events that consistently fail processing (e.g., by tracking attempt counts). These could then be manually or semi-automatically handled or moved to a separate location for investigation.
    * **Focus:** The primary guarantee is that events tied to successfully committed business transactions are reliably persisted and will eventually be processed.

## Section 7: Security & Performance

**1. Validation:**
    * **Library:** **FluentValidation** will be used across the ASP.NET Core backend for validating incoming Data Transfer Objects (DTOs) and request models.
        * **Applicability:** This applies to both **Controller-based APIs** and **Minimal APIs**. For Minimal APIs, FluentValidation will be integrated directly (e.g., via endpoint filters or extension methods) rather than introducing a larger meta-framework in this version.
        * **Rationale:** Provides a powerful, flexible, and testable approach to validation, consistent across different API styles. It is a widely adopted library in the .NET ecosystem, offering significant advantages over basic DataAnnotations for complex validation scenarios.

**2. Authentication & Authorization (Primarily for Configuration 2):**
    * **User Authentication Methods:**
        * **Google OAuth 2.0 / OpenID Connect:** For third-party authentication.
        * **Local Accounts:** Username/email and password-based. Passwords will be securely hashed using industry-standard algorithms (e.g., Argon2, scrypt, or PBKDF2 as specified in FSD). Credentials for local accounts will be stored in a **separate, security-focused database**.
        * **Account Linking:** For users authenticating via multiple methods with the same email.
    * **API Authentication (Backend to MAUI Client):**
        * **JSON Web Tokens (JWTs):** Access tokens and refresh tokens will be issued upon successful login. The MAUI client will be responsible for securely storing these tokens and sending the access token with requests to protected API endpoints.
    * **Authorization:**
        * **Role-Based Access Control (RBAC):** API endpoints will be protected based on user roles. Middleware will validate JWTs and associated roles. Initial roles will include `User` with considerations for a future `Admin` role.
    * **Modularity:** Authentication schemes will be configurable as per the FSD.

**3. Sensitive Data Protection:**
    * **Password Security:** Passwords for local accounts will be securely hashed (not encrypted).
    * **PII (Personally Identifiable Information - e.g., Shipping Addresses):**
        * **No Application-Level Field Encryption:** The template will **not** implement field-level encryption within the application code for PII like addresses.
        * **Protection Strategy:** Protection relies on a layered approach:
            * **Secure Transit:** HTTPS/TLS for all communications.
            * **Strong Application Access Controls:** Ensuring only authorized users can access sensitive data.
            * **Database-Level Encryption at Rest:** The architecture will assume that the chosen database hosting environment (e.g., PostgreSQL on a cloud service) will be configured to provide encryption at rest (e.g., TDE). This is an operational/DBA responsibility.
        * **Rationale:** Balances security with the complexity of the template. Field-level encryption introduces significant key management and performance challenges, best addressed based on specific compliance requirements of projects derived from the template.

**4. Latency and Query Optimization:**
    * **Core Strategies:**
        * **CQRS:** Separating read and write operations for optimized data access paths.
        * **Efficient Database Querying:** Adherence to best practices for writing database queries, including the strategic use of indexes (e.g., non-clustered GUID PKs, clustered INT/BIGINT PKs, other necessary indexes).
        * **Asynchronous Operations:** Consistent use of `async/await` for I/O-bound operations throughout the backend and in client-server communication to prevent blocking and improve responsiveness.
        * **Stateless Services (Backend):** Designing backend services to be stateless to facilitate horizontal scaling.
        * **Pagination:** Implementing pagination for API endpoints returning lists of data to manage payload sizes and improve client performance.

**5. Caching Mechanisms:**
    * **Configuration 1 (Standalone MAUI):** Application-level in-memory caching within the MAUI app for local data.
    * **Configuration 2 Frontend (MAUI Client):** In-memory caching for frequently accessed data like product lists and details to enhance UI responsiveness.
    * **Configuration 2 Backend (API):**
        * **Default Implementation:** **`IMemoryCache`** (in-process ASP.NET Core caching) for caching frequently requested, relatively static data (e.g., product catalog query results).
        * **Abstraction for Extensibility:** A caching service abstraction (e.g., `IServerCacheService`) will be defined. This design will clearly demonstrate how a distributed cache (e.g., Redis) could be integrated in the future by implementing this interface.
        * **Cache Invalidation:** Event-driven cache invalidation for `IMemoryCache` will be implemented, reacting to relevant domain events (e.g., product updated event invalidates cached product data).
        * **HTTP Caching Headers:** APIs will leverage HTTP caching headers (e.g., `Cache-Control`, `ETag`, `Last-Modified`) to enable client-side and proxy caching where appropriate.
    * **CDN (Content Delivery Network):** Considered out of scope for the V1 template, primarily relevant for future web frontends rather than the MAUI app and its API.

## Section 8: Observability & Maintenance

**1. Logging Strategy:**
    * **API Backend (Configuration 2):**
        * **Tool:** **Serilog** will be used for comprehensive logging.
        * **Content:** Logs will capture request details (path, method, status, duration), user information (if authenticated), correlation IDs, and detailed error information (stack traces, context). Sensitive data within logs will be masked.
        * **Storage:** Default to rotating log files. Documentation will provide guidance on configuring Serilog to sink to other destinations like a self-hosted database (e.g., PostgreSQL, SQL Server, Elasticsearch), with users responsible for the setup and retention policies of these external stores.
        * **Rationale:** Serilog is a flexible and powerful logging library for .NET, allowing for structured logging and a wide range of sinks. Rotating files are a sensible default for a template.
    * **MAUI App (Configurations 1 & 2):**
        * **Framework:** Utilize standard **`Microsoft.Extensions.Logging`** abstractions.
        * **Implementation:** A basic file-based logging provider will be demonstrated, adhering to best practices for mobile app logging (e.g., managing file size, rotation).
        * **Retention:** Local logs on the device will have a default maximum retention period (e.g., 7 days).
        * **Rationale:** Provides a standard and extensible way to implement logging in MAUI. File-based logging is practical for on-device diagnostics.

**2. Monitoring Strategy (API Backend - Configuration 2):**
    * **Metrics Collection:**
        * The template itself will not integrate a specific metrics collection agent.
        * **Guidance:** Documentation will recommend and guide users on setting up open-source tools like **Prometheus** for scraping metrics and **Grafana** for visualization. This includes metrics for request rates, error rates, response latencies, and system resource utilization (CPU, memory).
    * **Health Check Endpoints:**
        * **Implementation:** ASP.NET Core Health Checks (`Microsoft.Extensions.Diagnostics.HealthChecks`) will be implemented for the API backend.
        * **Content:** By default, it will report basic application health (e.g., app is responsive). Documentation will guide how to add checks for critical dependencies (e.g., database connectivity, external service availability if any).
        * **Security:** Implemented with security as a priority. This includes:
            * Guidance on exposing the endpoint on a non-obvious path or a dedicated port.
            * Recommendations for network-level restrictions in production (e.g., accessible only by internal load balancers or orchestration tools).
            * Ensuring the default endpoint does not expose sensitive diagnostic data publicly.
        * **Production Configuration:** The template will provide a functional health check endpoint with clear documentation on how to configure and secure it for production environments, including its use for liveness and readiness probes in container orchestrators (Docker Swarm, Kubernetes).
        * **Rationale:** Health checks are essential for automated monitoring and orchestration in modern distributed systems. ASP.NET Core provides robust built-in support.

**3. Alerting & Incident Management (API Backend - Configuration 2):**
    * **Strategy:** The template will **not include a built-in alerting engine.**
    * **Guidance:** Documentation will direct users to integrate collected logs (e.g., via Serilog sinks to Elasticsearch) and metrics (e.g., from Prometheus) with dedicated alerting tools. Examples include:
        * Prometheus Alertmanager for metrics-based alerts.
        * ELK Stack (Elasticsearch, Logstash, Kibana) with its alerting features for log-based alerts.
    * **Rationale:** Alerting setup is highly dependent on organizational preferences and existing infrastructure. Providing guidance on integration offers flexibility.

**4. Zero-Downtime Updates (API Backend - Configuration 2):**
    * **Architectural Support:** The backend architecture (stateless services, designed for horizontal scaling and load balancing) is inherently supportive of zero-downtime deployment strategies.
    * **Documentation:** The project documentation will discuss common zero-downtime deployment techniques (e.g., rolling updates, blue-green deployments) that are compatible with the template's architecture, providing conceptual guidance for implementers to apply within their specific CI/CD and hosting environments.
    * **MAUI App Updates:** Updates for the MAUI application (Configuration 1 or 2 client) are managed through the respective mobile platform app stores.
    * **Rationale:** While the template doesn't provide deployment scripts, guiding users on leveraging the architecture for high availability is valuable.

**5. Audit Logging:**
    * **Scope:** Explicitly **out of scope for V1** of the template.
    * **Rationale:** Audit logging requirements can be very domain-specific and add considerable complexity. This can be added by users based on their needs.

## Section 9: Folder Structure & Project Organization

**1. Guiding Architectural Principles:**
    * **Overall Pattern:** The solution embodies a **Modular Monolith** for the backend, strictly adhering to **Clean Architecture**, **Domain-Driven Design (DDD)**, and the project's custom **CQRS (Command Query Responsibility Segregation)** implementation.
    * **Rationale:** This combination provides a robust, scalable, and maintainable structure, emphasizing separation of concerns and clear domain modeling.

**2. Top-Level Directory & Solution Structure:**
    * **Root Directory:** `ProjectTemplateDotnet/`
        * **`build/`:** For Docker Compose files, build scripts, and CI/CD related artifacts.
        * **`docs/`:** Contains all project documentation (architecture, setup, guides, ADRs).
        * **`src/`:** Houses the .NET solution file (`.sln`), all C# source code projects (application, libraries, and **all test projects**).
        * `.github/workflows/`: For GitHub Actions CI workflow configurations (typically placed at the root `.github` folder, but build-related scripts can be in `build/`).
    * **Rationale:** Standard organization for .NET projects, with the specific directive to include test projects within the `src` folder, ensuring all code and related tests are co-located.

**3. Backend Project Organization (within `src/`):**
    * **Clean Architecture Layers:** Implemented via a set of distinct C# projects, ensuring clear separation of concerns:
        * **`Core/ProjectTemplateDotnet.Domain/`**: This project is central to Clean Architecture, containing entities, aggregates, value objects, domain services, repository interfaces, and domain events. Organization within this project is by **domain aggregate modules** (e.g., Products, Orders) to reflect DDD principles.
        * **`Core/ProjectTemplateDotnet.Application/`**: This project orchestrates domain logic. It includes application services, CQRS command definitions, query definitions, and their respective handlers, Data Transfer Objects (DTOs), and application-level interfaces (e.g., for caching, event dispatch, current user context). It is also organized internally by **domain aggregate modules**.
        * **`Infrastructure/`**: This layer consists of multiple projects that implement abstractions defined in the Core layers or provide technical capabilities:
            * `ProjectTemplateDotnet.Infrastructure.CrossCutting/`: For common infrastructure services like custom event dispatchers, the Outbox pattern processor, date/time providers, and caching service implementations (e.g., `IMemoryCache` wrapper).
            * `ProjectTemplateDotnet.Infrastructure.Persistence.EFCore/` & `ProjectTemplateDotnet.Infrastructure.Persistence.Dapper/`: These projects handle data access logic, providing concrete repository implementations using Entity Framework Core and Dapper respectively, along with DbContexts for EF Core.
            * `ProjectTemplateDotnet.Infrastructure.Identity/`: Manages local user authentication concerns, including password hashing and user management, potentially interacting with a separate authentication database.
            * `ProjectTemplateDotnet.Infrastructure.Realtime.SignalR/`: Contains the SignalR hub implementations and services for real-time notifications.
            * `ProjectTemplateDotnet.Infrastructure.AnalyticsStub/`: A placeholder for future analytics integration.
        * **`Api/ProjectTemplateDotnet.Api/`**: The ASP.NET Core project that serves as the entry point for HTTP requests. It's responsible for exposing API endpoints (via Controllers or Minimal APIs, organized by feature), request validation (using FluentValidation), authentication/authorization setup, health check endpoints, and logging configuration (Serilog). It will also contain the `Dockerfile` for containerization.
    * **Rationale:** This layered and modular structure enforces Clean Architecture, making the backend testable, maintainable, and adaptable to changes in infrastructure or presentation.

**4. Frontend Project Organization (.NET MAUI App within `src/Client/`):**
    * **`Client/ProjectTemplateDotnet.Maui/`**: A single .NET MAUI project designed to work for both Configuration 1 (standalone) and Configuration 2 (client to API).
    * **Internal Structure:** The UI and client-side logic are organized **by feature** (e.g., `Features/Products/`, `Features/Orders/`, `Features/Authentication/`). Each feature folder typically contains associated `Views` (XAML), `ViewModels` (adhering to the MVVM pattern), and any feature-specific models or client-side services.
    * **Shared MAUI Components:** Common elements such as base ViewModels, global resources (styles, images, fonts), MAUI application setup (`MauiProgram.cs` for DI, `AppShell.xaml` for navigation), general client-side services (API clients for Config 2, local data access services for Config 1, navigation services, dialog services), and configuration management are structured in dedicated, shared folders within the MAUI project.
    * **Rationale:** Feature-based organization enhances code navigation, maintainability, and scalability for the MAUI application, allowing teams to work on different features with less friction.

**5. Configuration, Environment Files, and Secrets Management:**
    * **Standard Practices:** Adherence to industry best practices and built-in .NET mechanisms:
        * **ASP.NET Core Backend:** Utilizes `appsettings.json`, environment-specific `appsettings.{Environment}.json` files, environment variables, and .NET User Secrets for development-time sensitive data. Typed configuration objects are populated using the Options pattern.
        * **.NET MAUI App:** Leverages `appsettings.json` (typically as an embedded resource) for application configuration, which is loaded into typed configuration classes. Secure storage for sensitive client-side data (like authentication tokens) utilizes platform-provided secure storage mechanisms.
    * **Rationale:** Ensures a consistent, secure, and flexible approach to configuration across different parts of the application and various deployment environments.

**6. Test Project Organization (within `src/Tests/`):**
    * **Structure:** Dedicated test projects are created for different types of tests (unit, integration) and for the various source projects they target (e.g., `ProjectTemplateDotnet.Domain.UnitTests/`, `ProjectTemplateDotnet.Application.UnitTests/`, `ProjectTemplateDotnet.Api.IntegrationTests/`, `ProjectTemplateDotnet.Maui.UnitTests/`).
    * **Rationale:** Provides clear separation of test code from production code, facilitates targeted execution of different test suites, and maintains organizational clarity, all while keeping tests co-located with source code under the `src/` directory as per the project's preference.
