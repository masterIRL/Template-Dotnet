# Project Template-Dotnet: Synthesized Architecture Design Document

Version: 1.0
Date: May 23, 2025

## 1. Core Project Vision & Objectives

* **Goal:** To create "Project Template-Dotnet," a .NET 9 boilerplate demonstrating best practices in **Clean Architecture, Domain-Driven Design (DDD), and a custom Command Query Responsibility Segregation (CQRS) implementation (explicitly avoiding MediatR)**. It will serve as a foundation for future projects, initially exemplified by a simple product purchasing application. 
* **Application Configurations:** 
  * **Config 1 (Standalone):** .NET MAUI mobile app with local data and no backend authentication. 
  * **Config 2 (Client-Server):** .NET MAUI app interacting with an ASP.NET Core API backend, supporting multiple authenticated users. 
* **Key Functional Pillars:** Product Catalog (with search), Order Management, simulated Finance & Shipping services, and modular Realtime Notifications. 
* **Core Cross-Cutting Concerns:** Modular authentication (Google OAuth/Local accounts), modular data persistence (SQLite/PostgreSQL, EF Core/Dapper), modular API styles (Controllers/Minimal APIs), localization, and performance optimization.

## 2. Hosting, Deployment & DevOps Strategy

* **Backend Hosting (Config 2):** Designed to be **cloud-agnostic**, promoting deployment flexibility. 
* **Containerization:** **Docker** is central, with Dockerfiles and docker-compose examples provided. The architecture is Kubernetes-friendly. 
* **CI/CD:** **GitHub Actions** for linting, unit/integration testing, and building artifacts (e.g., Docker images). Deployment steps are intentionally excluded from the template's sample pipeline. 
* **Infrastructure as Code (IaC):** Not included; left to the implementer. 
* **Scalability Focus:** The template emphasizes **scalable architectural patterns** (e.g., stateless services) rather than targeting specific traffic volumes.

## 3. Backend Architectural Design (.NET 9 & ASP.NET Core)

* **Core Principles:** **Clean Architecture** and **Domain-Driven Design (DDD)** are paramount. 
* **CQRS & Eventing:** A **custom, MediatR-free implementation** for commands, queries, and domain events, using defined interfaces and a DI-based dispatcher. Critical domain events leverage the **Transactional Outbox pattern** for reliable, at-least-once delivery, requiring idempotent event handlers. 
* **API Layer (Config 2):** Modular support for both traditional **ASP.NET Core MVC Controllers** and **Minimal APIs**. 
* **Data Access:** The **Repository Pattern** abstracts data persistence. Modular implementations for **Entity Framework Core** and **Dapper** are provided. 
* **Modularity:** Key backend concerns (Products, Orders, persistence, etc.) are designed as distinct modules within the Clean Architecture layers.

## 4. Frontend Design (.NET MAUI)

* **Framework:** A client-side **.NET MAUI** application for iOS and Android. 
* **UI Pattern:** **MVVM (Model-View-ViewModel)** is standard, streamlined by **CommunityToolkit.Mvvm** source generators for boilerplate reduction. 
* **Navigation:** **.NET MAUI Shell** provides structured, URI-based navigation. 
* **Styling:** Primarily **XAML Styling** (Styles, ResourceDictionaries, ControlTemplates), with supplementary use of built-in CSS capabilities where appropriate. 
* **Organization:** Feature-based project structure (e.g., Products, Orders features).

## 5. Data Management & Persistence Strategy

* **Database Technology:** **SQL databases**. 
  * **SQLite:** For Configuration 1 (local MAUI app data). 
  * **PostgreSQL:** For Configuration 2 (API backend and separate local auth credential store). 
* **Schema Migrations:**
  * SQLite: Managed by **EF Core Migrations**. 
  * PostgreSQL: Assumes **DBA-led or external script-based management**; the application adapts to the schema. 
* **Performance & Concurrency:** 
  * Strategic indexing (e.g., non-clustered GUID PKs, separate auto-incrementing clustered keys). 
  * Implementation of **Optimistic Concurrency Control** for relevant use cases. 
* **Consistency:** **Strong consistency** for command operations (transactional). Aim for the **lowest possible latency** for query operations (CQRS read models). Client UI operations are asynchronous. 
* **Product Search:** Relies on **database-intrinsic capabilities** (e.g., SQL LIKE, Full-Text Search); no third-party search engine integration in the base template. 
* **Multi-Tenancy:** Not supported.

## 6. Event Handling & Asynchronous Operations

* **Asynchronous Processing:** Fundamental for UI responsiveness, inter-module communication (via domain events), and offloading tasks. 
* **Event Sourcing:** Explicitly out of scope. 
* **Domain Event Mechanism:** Custom DI-based dispatcher for IDomainEventHandler\<TEvent\> implementations, integrated with the **Transactional Outbox pattern** for critical events to ensure reliability and at-least-once delivery. Event handlers must be idempotent. 
* **Real-time Client Updates:** **SignalR** is the chosen technology, implemented modularly with abstractions.

## 7. Security & Application Performance

* **Input Validation:** **FluentValidation** used consistently across both Controller-based and Minimal APIs in the backend. 
* **Authentication (Config 2):** 
  * Google OAuth 2.0 / OpenID Connect. 
  * Local accounts with securely hashed passwords (credentials in a separate, dedicated database). 
  * Account linking for unified user identity. 
  * **JWTs (JSON Web Tokens)** for API authentication. 
* **Authorization (Config 2):** Role-Based Access Control (RBAC) for API endpoints. 
* **Sensitive Data (PII):** Protection via secure transit (HTTPS), strong application access controls, and reliance on **database-level encryption-at-rest** (operational concern). No application-level field encryption is implemented by the template. 
* **Performance Optimization:** CQRS, efficient database querying, asynchronous operations, stateless backend services, pagination for APIs, and strategic caching. 
* **Caching Strategy:** 
  * MAUI Client: In-memory caching. 
  * API Backend: Default **IMemoryCache** (in-process), with a robust abstraction layer to facilitate future integration of distributed caches (e.g., Redis). Event-driven cache invalidation for IMemoryCache and use of HTTP caching headers.

## 8. Observability & System Maintenance

* **Logging:**
  * API Backend (Config 2): **Serilog** for comprehensive structured logging (default to rotating files, with guidance for custom sinks).
  * MAUI App: Standard **Microsoft.Extensions.Logging** abstractions (default to local file provider).
* **Monitoring (API Backend \- Config 2):**
  * Guidance for using **Prometheus & Grafana** for metrics.
  * Secure and configurable **ASP.NET Core Health Check endpoints** implemented for liveness/readiness probes.
* **Alerting:** No built-in alerting engine; documentation will guide integration with external tools (e.g., Prometheus Alertmanager, ELK).
* **Zero-Downtime Updates (API Backend \- Config 2):** The architecture (stateless services, load balancing) supports this. Documentation will discuss common strategies.
* **Audit Logging:** Out of scope for V1.

## 9. Project & Code Organization

* **Overall Structure:** The backend is a **Modular Monolith** adhering to **Clean Architecture**.
* **Top-Level Directories:** src/ (containing all source code and test projects), docs/, build/.
* **Backend Project Layers (within src/):**
  * Core/Domain/ & Core/Application/: Central layers, organized internally by domain aggregate modules (e.g., Products, Orders).
  * Infrastructure/: Multiple projects for data persistence (EFCore, Dapper), identity, cross-cutting concerns (event dispatchers, outbox), and external service integrations (SignalR).
  * Api/: ASP.NET Core project for API endpoints.
* **Frontend (.NET MAUI in src/Client/):** Organized **by feature** (e.g., Features/Products/, Features/Orders/).
* **Configuration:** Standard .NET practices (appsettings.json, environment variables, user secrets).
* **Testing (within src/Tests/):** Separate projects for unit and integration tests, organized by the project under test.
